# Migration — v1.0.1 → v1.1.0 (scalable durable SQLite ledger)

This document describes how `dsh-token-usage-sidebar` upgrades the persistent
accounting store from the v1.0.1 monolithic root-JSON ledger to the v1.1
plugin-owned SQLite ledger. The migration is automatic, verified, idempotent, and
fail-closed.

## Source and destination

- **Source (v1.0.1):** a single JSON ledger at
  `${DSH_HOME:-~/.dsh}/storages/dsh_token_usage_sidebar.json`
  (`tables.ledger.root`), schemaVersion 4, holding `byId`, `detailBy`, `dayBy`,
  `seqBy`, `src`, and the live/historical split.
- **Destination (v1.1):** a SQLite database at
  `${DSH_HOME:-~/.dsh}/storages/dsh_token_usage_sidebar.sqlite` (+ `-wal`/`-shm`),
  using Node's built-in `node:sqlite` (WAL journal).

## Migration steps (run once, on first startup after the v1.1 upgrade)

1. **Detect** the v1 JSON ledger; if absent (fresh install), skip migration and start a
   fresh ledger.
2. **Validate** the v1 ledger read-only. It is only ever read or copied.
3. **Back up** the v1 ledger to an immutable, timestamped
   `dsh_token_usage_sidebar.json.pre-v1.1-<timestamp>.bak` in the same directory.
4. **Create/open** the SQLite DB and its schema, with `migration_status=in_progress`.
5. **Insert** the canonical records (`usage_records`) from the v1 ledger, keyed by
   `canonical_id = sessionId:turn:step`, using an upsert keyed on that id.
6. **Derive** the aggregate tables (`aggregate_global`, `aggregate_daily`,
   `aggregate_model`, `aggregate_day_model`) from the records.
7. **Verify** accounting equivalence: `lifetimeTotal`, `recordCount`, and
   `sum(usage_records.total_tokens) == aggregate_global.total_tokens`.
8. **Cutover** — only if verification passes: set `migration_status=done` and switch
   reads to the SQLite ledger.
9. **On any mismatch:** set `migration_status=failed`, remove the just-inserted records
   (fail-closed), keep the v1 source intact, and do **not** cut over.

## Guarantees

- **Idempotent.** A `done` migration short-circuits on later restarts. Re-running the
  migration never duplicates rows or drifts totals.
- **Crash-safe.** The v1 source is read/copied only; SQLite transactions are atomic.
  A crash mid-migration leaves the DB without a `done` marker, so the next startup
  re-runs migration idempotently. Records from a failed migration are removed.
- **Fail-closed.** No unverified record ever becomes visible; no cutover without
  exact-equivalence verification.
- **Exactly-once.** Live collection does not start until migration/cutover completes,
  so a live event cannot race the cutover and be lost or double-counted. New records
  after cutover are exactly-once by canonical id (higher-seq wins).
- **No token loss.** The v1 source is backed up and never deleted.

## Downgrade (v1.1 → v1.0.1)

`dsh-token-usage-sidebar` v1.0.1 cannot read the v1.1 SQLite ledger. To return to
v1.0.1, restore the pre-upgrade v1 JSON ledger (the untouched v1 source or its
`.pre-v1.1-*` backup) after reinstalling v1.0.1. The v1.1 SQLite files can then be
removed.

## Verification of a real ledger

The migration was exercised against a copy of a real v1 ledger. See the release
report for the exact before/after `recordCount` and `lifetimeTotal`, which must be
equal (delta 0) after migration.
