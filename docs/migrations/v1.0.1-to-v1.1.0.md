# Migration — v1.0.1 JSON → SQLite

The automatic migration validates the source, imports its records as a union with
existing SQLite history, verifies all derived totals, and commits cutover atomically.
This document includes the rollback/integrity fixes released in v1.1.9.

## Source and destination

- Source: `${DSH_HOME:-~/.dsh}/storages/dsh_token_usage_sidebar.json`,
  `tables.ledger.root` with byId/detailBy/dayBy/seqBy/src metadata.
- Destination: the same storage directory's `dsh_token_usage_sidebar.sqlite`
  and its WAL/SHM companions. Paths are independent of the npm package name.

## Steps

1. Distinguish an absent source (fresh install) from an unreadable/invalid source.
   Validate each record and check that the declared lifetime total and record count
   match the source records. Invalid storage is never treated as an empty ledger.
2. Copy a valid source to an immutable
   `dsh_token_usage_sidebar.json.pre-v1.1-<timestamp>-<uuid>.bak`. The source remains
   read-only. A backup failure prevents cutover.
3. Begin an immediate SQLite transaction. Capture the previous destination rows/totals
   under the write lock and mark migration in progress.
4. Import records by canonical identity. Preserve unrelated destination records,
   newer overlapping samples and rows already reconciled to accounting version 2.
   Equal-sequence, equal-total records may enrich missing metadata.
5. Derive every aggregate from valid active records. Verify imported record identity,
   the destination union total, all bucket/count fields and provenance. A nonempty
   destination need not equal the source total: it also contains independent history.
6. Set migration_status=done in the same transaction and commit.
7. On validation/write/verification failure, roll back all imported/replaced rows,
   aggregate changes and transaction metadata. Set the failed marker afterward.
   Never delete by attempted IDs as a substitute for rollback; an overlapping ID
   may have existed before migration.

## Guarantees and API behavior

- A completed migration short-circuits without rereading the old JSON root.
- A process interruption before commit leaves the previous SQLite state intact;
  the next startup can retry. The JSON source and backups are never removed.
- A failed migration does not serve successful empty/partial cutover totals.
  Summary/details return HTTP 503 with error/health; debug reports the failure.
- Live listeners are registered before asynchronous session recovery. Persisted
  usage and recovery checkpoints commit together.
- JSON source discovery is separate from cutover: later changed plugin-owned units
  can be rechecked and imported; aggregate-only summaries never become synthetic calls.
- This migration retains legacy accounting version 1. A complete authoritative
  replay can separately perform [the audited accounting v2 correction](accounting-v2.md).

## Downgrade

v1.0.1 cannot read SQLite. Stop the relevant DSH profile before restoring its old
JSON source/backup for a downgrade. Preserve the current SQLite, WAL/SHM and backups
in an archive so later usage is recoverable; do not delete them.

The pre-upgrade JSON does not include newer SQLite-only usage. Restoring an older
snapshot is not a merge, and later usage must remain available in the retained files.

## Validation

Synthetic regressions cover empty sources, source integrity, preexisting unrelated
history, newer overlaps, verified cutover, restart idempotence, late verification
failure with exact transactional restoration, and immutable source backups.
